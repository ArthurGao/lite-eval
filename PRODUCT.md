# Product

## Platform

web

## Users

Two audiences, weighted equally (owner, 2026-11-14):

- The owner, evaluating their own AI projects (lite-rag, lite-mem, llm-steward) on a local machine. Fluent in the
  vocabulary: hit@k, MRR, McNemar, bootstrap intervals, baselines, gates.
- Other engineers who adopt lite-eval from the public repository for their own RAG, memory, extraction or agent
  systems. They know their system but may meet lite-eval's terms and statistics for the first time.

Both use the Viewer the same way: after changing a system and running a suite, they open it on their machine to
decide whether the change made things better or worse, and whether the difference can be trusted.

## Product Purpose

lite-eval answers one question for any AI system it can call: did this change make it better or worse, and can we
trust that? The Viewer (`lite-eval view`, loopback only) is where a human reads the answer: runs, paired
comparisons with significance, every case, and the triage of misses one by one. Success: a person can go from
"I changed X" to "these N cases regressed, these are real misses, these are label errors" without leaving the page,
and never mistakes noise for a result.

## Positioning

The numbers carry their own doubt. Every comparison is paired and says when a difference is not significant and how
much one case is worth; partial runs, warnings and synthetic datasets are marked wherever they appear. Run records
are immutable files in the user's repository, and the Viewer only reads them (its single write is an annotation).

## Operating Context

- Main workflow (owner, 2026-11-14): change a system, run a suite, open the Viewer, compare against the baseline,
  open the regressed cases, triage misses (real miss / label wrong / excluded / unclear). The Runs list is the way
  in; Compare and Miss triage are the main working surfaces.
- Secondary: browse a dataset and flag a wrong label; follow one metric over time across baseline switches and
  dataset versions.
- Sessions are long and focused; the user often switches between the Viewer, the terminal (`lite-eval run`,
  `compare`, `triage`) and their editor.
- A run or a comparison can be exported as one self-contained HTML file and sent to someone else, who opens it from
  disk with no server and no lite-eval install.

## Capabilities and Constraints

- Pages (design `docs/lite-eval-design.md` §10.1): Runs, Run detail, Compare, Case detail, Miss triage, Datasets,
  Trends.
- No statistics in the browser: metrics, deltas, significance, warnings and "one case = x points" come from the API
  and are shown as given.
- The only write is an annotation; nothing edits runs or datasets.
- The same build serves the live Viewer and the exported HTML file, so it must work offline from a single file:
  no web fonts, no network assets, no code splitting.
- The backend's OpenAPI spec (`backend/openapi.json`) is the only contract; the client is generated from it.
- Terms used throughout: run, suite, config, case, scorer, metric, baseline, miss, annotation, dataset version.

## Evidence on Hand

- Real run records: lite-rag's golden set (32 questions, 3 retrieval configs) under
  `~/Code/AI/lite-rag/eval/lite-eval/` (gitignored there; usable for local screenshots).
- Test fixtures are generated by `backend/tests` with the fake target; no real customer data exists or may be added
  (AGENTS rule 11).
- No testimonials, users or benchmarks to cite; none may be invented.

## Product Principles

1. Doubt is as prominent as the number: a non-significant difference never looks like a win or a loss.
2. Regressions first: whatever got worse is listed before whatever got better.
3. Every case is one click from the number it moved.
4. The Viewer explains its terms where a newcomer meets them, without slowing down someone who already knows them.
5. Nothing on screen depends on the server once exported: the file is the record.

## Accessibility & Inclusion

Confirmed by the owner (2026-11-14):

- Fully keyboard-operable: lists move with J/K, triage categories have single-key shortcuts, every dialog is
  reachable and dismissible from the keyboard.
- WCAG 2.2 AA contrast in both light and dark themes, including status colours.
- Colour-blind safe: regressed / improved / not significant are never told apart by red and green alone; each also
  carries a sign, word or symbol.
